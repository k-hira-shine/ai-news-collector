# ポストモーテム: X収集9割減と検知すり抜け（2026-06-21〜06-23）

> 1枚で「原因・結果・解決策」を把握するための要約。詳細経緯は `handoff.md` の
> 「2026-06-22 追補」「2026-06-23 追補2/追補3」各節を参照。

## TL;DR
- **何が起きたか**: 外部Apify actorの仕様変更でX収集が約9割減。1回目の修正が2経路のうち1経路しか直さず、残り経路（must_follow）が劣化したまま2日間気づかれなかった。
- **なぜ気づけなかったか**: 異常検知が「直近中央値比」の相対判定だけで、劣化が続くとベースラインごと崩れて崩落値すら平常に見えた（＝検知の構造的盲点）。
- **どう直したか**: 両経路を「1アカウント/1クエリ = 1 run」に統一し、検知に「経路別の絶対フロア」を追加。過去3障害日を初日から検知できることを実ログ再生で確認。

---

## 1. 原因（Root Cause）

### 1-1. 発端＝外部要因（こちらのコードは無変更）
X検索は Apify actor `xquik/x-tweet-scraper` に複数の検索語/アカウントを投げる。
2026-06-21 の actor 新ビルド（`tVcWiwAfiLajn6Qbb`→`aw35GGxixnBFEFrJj`）で
**`maxItems` の実効挙動が「検索語ごとの上限」→「全searchTerms合算の上限」に変化したと観測**。
複数語を1 runにまとめていた旧実装では、先頭の語が枠を食い潰し後続の語が
budget=0 で飢餓 → **X収集が 95→7件（約9割減）に崩落**。

### 1-2. 1回目の修正の取りこぼし（incomplete fix）
6/22に `collect_x_twitter` を per-query 化したが、この関数には X検索が**2経路**ある:

| 経路 | 6/22時点 |
|---|---|
| `search_queries`（検索語） | per-query 化した ✅ |
| `must_follow`（必須アカウント） | `searchTerms=[全30アカウント]` のバッチのまま放置 ❌ |

両者は**構造的に同一の呼び出し**（バッチ `searchTerms` + 共有 `maxItems`）なのに
片方しか直さなかった。**全 call site を grep で洗わなかった**のが直接原因。
must_follow 側の症状は「0でなく薄い(8件)」で目立たなかった。

### 1-3. 検知がザルだった（baseline poisoning）
`daily_check.py` の急減検知が**すべて「直近full便の中央値」比の相対判定**だった。
劣化が数日続くと**ベースライン自体が劣化値で埋まり、崩落値すら平常に見える**。実データ:
```
6/23朝便を最新とみなした時の must_follow急減判定:
  baseline = median([5, 6, 17, 8]) = 7   ← 全部が障害期間中の値（汚染）
  判定: cur=8 < 0.2*7=1.4 ? → False（発火せず）
```
＝相対のみの検知は、**持続的劣化／メトリクス履歴の開始直後の劣化**に構造的に盲目。
閾値0.2（5倍減でやっと）も緩すぎた。

### 1-4. 判断ミス（aggregate trap）
6/23朝の確認で `x_valid=80` と daily_check 全緑だけを見て"回復"と早合点。
健全ベースライン(206〜528)と突き合わせず、経路別にも切り分けなかった。
緑だったのは 1-3 の盲点が原因＝**誤断と検知のザルは同じ根**。

## 3. 解決策（Resolution）

### 3-1. コード修正（両経路を独立runに統一）
- 検索語: 1クエリ=1 actor run（`searchTerms` 常に1語・6/22 `15f3174`）。
- must_follow: **1アカウント=1 actor run**（6/23 `986689c`）。
  → `maxItems` がクエリ/アカウント毎に効き、actorの解釈変更に今後も依存しない。
  → 主要課金は結果従量制（$0.00015/件）のため、同一取得件数なら大きなコスト増は想定しにくい。今回の検証範囲でもコスト増は問題化していない。

**本番検証**（workflow_dispatch run 27979622316・success）:
must_follow_raw **30→148** / must_follow_final **8→82** / X合計 **80→211** / items **27→91** に回復。

### 3-2. 検知のハードニング（経路別の絶対フロア）
`daily_check.py` に**固定フロアを本判定として追加**（full便のみ・`a8dacf3`）:

| 定数 | 値 | 根拠 |
|---|---|---|
| `FULL_X_VALID_FLOOR` | 120 | 健全206〜 / 障害39〜80 を分離 |
| `FULL_ITEMS_FLOOR` | 40 | 健全69〜 / 障害7〜27 を分離 |
| `FULL_MUST_FOLLOW_FLOOR` | 25 | 健全69〜92級 / 障害5〜8 を分離 |

- 相対と違い**履歴汚染に強く、劣化初日から検知**。
- 収集品質detailに `x_valid` を表示＝経路別の痩せを目視でも切り分け可能に。
- 相対の急減検知/advisoryも残し、フロア上での大変動を拾う**二段構え**。

### 3-3. 取りこぼし再発防止（横断不変条件テスト）
`collect_x_twitter` の**全 actor 呼び出しが `searchTerms` 1語**であることを固定する
テストを追加。3本目の経路がバッチで足されても即CI落ち。

### 3-4. 検証（実ログ再生）
過去の障害データを新検知に通すと全て初日から検知、修正後データは合格:
```
6/21 items7/mf5/x39   → ❌（旧は素通し）
6/22 items12/mf6/x44  → ❌（旧は素通し）
6/23 items27/mf8/x80  → ❌（旧は素通し＝見逃した値）
6/23 items91/mf82/x211 → ✅合格
```

### 3-5. 慢性側の穴も追加で閉塞（2026-06-23 追加）
フロアは「崖（単日の崩落）」を捕まえるが、その上で続く中規模劣化は拾えなかった。2つ追加:
- **じわ減り検知（本判定）**: 汚染されない**固定の健全リファレンス**比で、痩せが2連続したら要確認。
  `HEALTHY_REF={x_valid:300, items:110, must_follow:80}`・`EROSION_FRACTION=0.5`・`EROSION_STREAK=2`。
  例: must_follow が floor(25)の上の 35→30 と続いても検知（単発の閑散日は許容）。
- **単一 critical アカウント沈黙（advisory）**: 合計 must_follow が健全でも、特定 critical アカウントの
  黙り（ハンドル変更・個別収集断）は隠れる。collector が per-account 件数を記録→`must_follow_critical_zero`
  を永続化→daily_check が3連続ゼロの handle を ⚠ 表示（個人は数日沈黙し得るため非failing）。

テスト全150件 green。

## 4. 教訓（Lessons）
1. **同一構造の処理が複数あるなら全 call site を grep で洗う**。症状の見える1箇所だけ直さない。
2. **相対(ベースライン比)の異常検知は持続的劣化に弱い**。健全実測から引いた絶対フロアと併用する。
3. **回復は総量でなく経路別に判定する**。緑のダッシュボードを劣化後ベースラインで読むと誤断する。
4. **不変条件はテストで固定する**（「全呼び出しは1語」のような横断ルール）。

## 5. 残リスク / Follow-up
- 固定フロア／健全リファレンスは現在の full便実測に基づくため、検索クエリ数・must_followアカウント数・収集ウィンドウを変更した場合は再調整する（`daily_check.py` 冒頭の定数に集約・根拠コメントあり）。
- 6/24朝便の scheduled run でも、手動dispatch同様に must_follow が同水準に戻ることを確認する（handoff 次回#0）。
- critical 沈黙advisoryは新フィールド `must_follow_critical_zero` を使うため、full便履歴が3件貯まる6/25頃から有効化（それまで沈黙が正常）。
- Apify actorの挙動変更に備え、障害時は actor build ID / input / output 件数分布の差分を即確認する。
- 件数が落ちない劣化（取得の質低下・出力スキーマ変更など）は依然フロア/じわ減りでは捕まらない＝既知の残課題。
